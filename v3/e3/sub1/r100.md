## IQR's code (read from `forks/radiance-twopass`, IQR-V3 / V4)

- **Value.** `q(s) = bytesum(((s·A + B) mod 2^32) & 0x3F3F3F3F) − 126`: the low 6 bits of each byte of a
  multiplicative hash, summed, so an integer in [−126, 126] on the int8 grid. Over the 65,536 16-bit states it
  spans −117..120 (238 values), sd 36.94 (Irwin–Hall of four uniform 0..63). Decode: `v_mad_u32_u24`, `v_and`,
  `v_dot4` (`sudot4(h, 0x01010101, −126)`), see `libr4d/r4d_iqr_dec.h:290-303`. Host reference: libquant
  `tcq_lut_mad` (`libquant/lq_grid.cpp:1151`). I checked that our numpy copy matches the C formula on all 65,536 states.
- **A and B are not searched.** They are libquant parameters `tcq_a` / `tcq_b` with defaults A = 0xB5297B (24 bits;
  `& 0xFFFFFF`), B = 0x2545F491 (`lq_grid.cpp:438-440`, `lq_quant.h:38-39`). No recipe, tool or doc in the tree sets
  them, and the IQR-V3 report names these two constants for the whole model. They are stored per tensor
  (`trellis.mad` plane: the 2^L table "kept for the unrelayout", then A and B, `r4d_iqr.h:49-50,127`) only because the
  format allows other values; the kernels read them from the aux block. So **no `iqrh_tuned` was built**: there is
  nothing per tensor to tune. The side search below asks instead whether a better *global* A exists.
- **Trellis.** It is the same bitshift trellis as EXL3's: `state_r = (state_{r−1} << k | code_r) mod 2^L`, value at
  the new state, k = 2..7 integer bits. L = 16 (15 for the 2-bit base, where IQR's card-side search holds only 2^15
  states). Differences that don't touch the codebook question: IQR runs the trellis down a weight column in
  tail-biting runs of 256 rows (V4: 512 / 1024 for the FFN), where EXL3 runs it over a 16×16 tile (256 values,
  tail-biting). IQR has no fractional K. Its scale is one f32 per row with a searched gain (`tcq_gain`); ours is
  the proxy's per-row RMS × a global factor grid. So `iqrh` in `trellis4.py` is IQR's value map on our 16-bit
  states, divided by its sd (unit scale like the other proxy codebooks). Fractional K (0.25 / 0.5 / 1.5 / …) uses the
  proxy's salted 0-bit steps with this codebook, which IQR doesn't have.

## VALU ops per decoded value (from the source; no gfx1201 compiler on the CPU boxes; the GPU box was busy)

State extraction (ours, `exl3r4d_common.hip.h` `decode_run`, per value): K = 4: 0.75 (v_perm, v_alignbit, v_perm a
run of 4); K 1–5: 1.75 (alignbit + 4 v_bfe + 2 v_lshl_or); K 6–7: 2.25. It is the same for any codebook on our
format, so it is listed apart from the codebook part (state → value):

| codebook, output | sequence (per value unless "a pair" / "a quad") | codebook part | + extraction K4 / K≠4 |
|---|---|---|---|
| mul1 → f16 (V2) | hash a pair: 2 v_pk_mul_lo_u16 + 2 v_mad_u32_u16; v_sad_u8 + v_sad_hi_u8 a pair; v_pk_fma_f16 a pair | **3.5** | 4.25 / 5.25 |
| mul1i8 → f16, today (`exl3i_i8_pair`) | mul1 → f16, then a pair: 2 × (cvt f16→f32, mul, rndne, clamp (med3 or max+min), mul, cvt f32→f16) + pack | **≈ 9–11** (detour 5.5–7.5) | ≈ 10–12 / 11–13 |
| mul1i8 → int8, today (wdec8) | the line above, then `exl3i_a8_wq` (cvt, mul, rndne, cvt_i32) + byte packing | **≈ 14–17** | ≈ 15–18 / 16–19 |
| mul1i8 → int8, closed form (notes P2 / K#2, bit-exact, **not built**) | hash 2; a pair: sad_lo + sad_hi (bias 3), v_pk_lshrrev_b16, v_pk_max_u16; a quad: v_perm + v_xor 0x80808080 | **4.5** | 5.25 / 6.25 |
| mul1i8 → f16, closed form (K#1, not built) | the closed form's u16 pair, then v_or 0x6400 + v_pk_fma_f16 a pair | **5.0** | 5.75 / 6.75 |
| **iqrh → int8** | v_mad_u32_u24, v_and 0x3F3F3F3F, v_dot4 (−126 in the accumulator); a quad: 3 v_perm (pack) | **3.75** | 4.5 / 5.5 |
| **iqrh → f16** | v_mad_u32_u24, v_and; a pair: sad_lo / sad_hi into 0x6400 halves (1024 + q + 126, exact in f16), v_pk_fma_f16 | **3.5** | 4.25 / 5.25 |
| (IQR's own M = 1 GEMV, int8 activations) | v_mad_u32_u24, v_and, v_dot4 against the broadcast activation byte = decode **and** multiply-add | 3 | (IQR-V3 Table 2: 336 VALU / 64 weights incl. its extraction = 5.25) |

The hash costs the same (2 a value: mul1's packed pair vs IQR's mad + and). IQR's gain is all in the
rounding: its values are integers already, and the byte sum plus bias is one instruction.
- vs **today's** mul1i8: f16 ≈ 9–11 → 3.5, int8 ≈ 14–17 → 3.75 (codebook part), i.e. −60–75%.
- vs the **bit-exact closed forms** (no requant needed): f16 5.0 → 3.5 (−30%; with extraction −22% at K≠4, −26%
  at K4); int8 4.5 → 3.75 (−17%; −12% / −14% with extraction). iqrh on f16 equals mul1's cost (V2's).
The f32 detour's exact count depends on whether clang folds the conversions into `v_fma_mix*` and the clamp into
`v_med3`, hence the ranges. A disassembly on a ROCm box would pin it down (2 minutes).

## Side search: a better global A (iid tiles, no weights, no calib)

`r100asearch.py`, cpu2, single-thread jobs. Plain trellis MSE on iid N(0,1) tiles, best of scale 0.9 / 1.0 / 1.1,
B fixed to IQR's, ratio against mul1_i8 on the same tiles.
- Stage 1: 1,024 random odd A in [2^20, 2^24) plus IQR's, 128 tiles (seed 11), K2 and K4. Medians were ×1.027 (K2)
  and ×1.025 (K4); minima ×1.009 / ×1.002. IQR's A scored ×1.014 / ×1.024, better than 95% of the random A at K2
  and about the median at K4. **No A reaches mul1_i8 at K2.**

So the code family (6-bit-masked bytes of a 24-bit multiplicative hash) has a floor near +1% at K2–3 whatever A
is. The high-K loss depends strongly on A: with K bits shifted in, the 2^K successors of a state differ only by
j·A, j < 2^K, and some A spread those values over the line much worse than others. 0xd0474b was then run on the
20 real tensors at K2–6 (`r100.sh c`, method `ldlq_iqrh:0xd0474b:0x2545f491`; side table in the report). It costs the
same to decode (only the constant changes). If iqrh is adopted, use a searched A rather than IQR's. A wider search
(B too, more candidates, scored at K4–6) would probably find better still.

## How it was run (reproduce)

Code dirs (copies of `e3.py trellis.py trellis2.py trellis4.py viterbi.c` + `sub1/r100*.sh`; `libviterbi.so` built
there with `gcc -O3 -march=native -fopenmp -shared -fPIC viterbi.c -o libviterbi.so`): cpu1 `/data/work/e3t/r100/`,
cpu2 `/data/work/e3t100/` (A search in its `sub1/`).
- `./r100check.sh`: the mul1_i8 check (cpu2, ~8 min).
- `./r100.sh a 10 4` (cpu1: 10 jobs, at most 4 ffn_down), `./r100.sh b 20 10` (cpu2). A job = (tensor, codebook,
  K chunk), resumable (skips chunks already in the output); `DRY=1` lists what's left. Ten simultaneous ffn_down
  starts on cpu2 hit the 128 GiB cap once (2 OOM kills, both at load; an ffn_down job holds 9.8 GB once loaded,
  more while loading). The killed chunk was rerun.
- Load balancing: cpu1's 15 not-started part-a jobs were moved to cpu2 (`r100fill.sh JOBFILE MAX`, output
  `r100-a2.jsonl` there), and the queue was stopped by killing cpu1's xargs only, so the running jobs finished.
  `r100fill.sh` also takes `MEMGB` / `GAP` for ffn_down.
- Tuned A: `CBS=iqrh:0xd0474b:0x2545f491 CHD="2 3 4 5 6" CHO="2,3 4,5 6" ./r100.sh c ...` plus fills on both
  machines.
- A search: `r100asearch.py 128 2,4 11 rand:S:256 as1-S.jsonl` for S = 1..4, then `r100asearch.py 512
  1,2,3,4,5,6,7 12 A1,A2 as2-A1.jsonl` on the top 8. `r100iid.py` is the quick VM version.
- Report: `python3 r100report.py r100-results/r100-*.jsonl`.
Wall time: 2:14–4:55 AM CST (main sweep done 4:28). CPU ≈ 70 core-hours (cpu2 ~1.4× faster a job than cpu1).
**Runtime cost of the change** (INDEX column): iqrh would change **decode and prefill** (cheaper codebook ALU, table
above), with a quality cost per this table. The proxy itself changes nothing.
