# EXL3-V3 design (started 2026-10-31; scope current as of 2026-11-05)

"Goal and scope" below is the current plan and matches `docs/ROADMAP.md`. The numbered sections keep their dated
decisions and measurements; where one conflicts with "Goal and scope", the scope wins, and superseded statements are
marked **[superseded YYYY-MM-DD]**. Open decisions are marked **[decide]**. Measurements from the first outline
(2026-10-30) are Appendix A; experiments live in `../experiments/`.

## Goal and scope

- **Speed:** the board scores trunk GEMM time per decoder layer at 2048 tokens (`gemm_us`). V1/V2's EXL3 kernel:
  ~8,050 µs. IQR-V4's int8 path: ~3,970–4,040; FP8: 3,712. **Fast variant target: ~4,000–4,300 µs** (two-pass
  int8 prefill, est.), lower where A4 pays at ≤ 3 bpw; accurate variant on the two-pass f16 plane (est. ~6,000–7,000;
  IQR's f16 trellis path 5,908). Decode is not optimized in V3 (later work, user 2026-11-05).
- **Sizes (user, 2026-11-04 / 11-05):** quality work targets **2.5–4.5 bpw** (real-use thresholds ~0.01–0.04 KLD,
  the 12–32 GB VRAM tiers); 2.0 and 5.0 as end points; 6.0; **7.0** (11-05; supersedes "nothing above 6"); 8.0
  decided after the 7.0 and a floor split on V2 8.0 (built only if predicted ≥ 10% below V2 8.0's 0.00034); 7.5 stays
  V2. **Research points 1.5 / 1.75**, then a **low-bpw research ladder** in 0.1 bpw steps below 1.5 (1.4, 1.3, ...)
  until KLD blows up (user, 2026-11-05; 1.25 dropped as a separate point) (saturation-aware allocation for these). **Sub-1 K (K0.125–0.875 at 1/8 steps) is in V3** (11-04,
  supersedes the 11-01 "V3.5" decision): the quantizer and every decoder get the salted 0-bit read; knap4 offers
  sub-1 at every size once #90 prices it.
- **Variants (user, 2026-11-04 / 11-05):** each size in an *accurate* (f16 wherever it lowers KL) and a *fast* variant
  (int8 path wherever its KLD cost is small, under a speed budget), both from knap4 with per-tensor compute modes; a
  third, *A4* variant at ≤ 3 bpw only if its knapsack point is ≥ 15% lower `gemm_us` than the fast one.
- **Weights × compute modes:** the W/A table in §1. A4 on i4 weights is a per-tensor knapsack option for the fast
  variant at ≤ 3 bpw (#46-03; supersedes "A4: not in V3").
- **Ladder (user, 2026-11-04):** i4 codebook K0.125–K3 at 1/8 steps (24 levels; upper end per #90-02); i8 K2–K5 at
  1/8 steps and K5.25–K7 at quarter steps (33); mul1 (unrounded, f16 path) K6–K8 at quarter steps (9). 66 levels,
  ~180 card-hours at ~2.75 h a level; quantized in order of use (2.5–4.5 first) once the quantizer settings are
  frozen. Deliberately finer than the knapsack strictly needs. bf16 stays a menu option without a run. Healing per
  ladder level (a library: 79–85% of per-mix healing, 96–97% with a polish pass).
- **Quantizer stack** (each item needs its 27B confirmation, `../experiments/BACKLOG.md` "27B confirmation queue"):
  diagonal output Hessian **H_out = Σdy², block-normalized** (#33-27; the 27B swap test #33-28 decides) → **swj**
  (joint SwiGLU scale refit, #85) → **writers asym ρ0, last** (#87) → **frozen-code scale healing** (#89; needs the
  user's go-ahead for the 27B; open whether it is in V3 for ≤ 3.5 bpw). Also: per-tensor damping, scale gain,
  turboderp's tensors as options (§1d). To test: IQR-V4's act order (16-column blocks, free at runtime), bf16
  (row, 128) scales on attn_output / ssm_out from K5, a vocabulary-weighted head vs the row-slab head; A1 up-only
  (down_proj predicted from up, #81) as a per-layer option if it is on the frontier; self-calibrated statistics
  (#91). i8c is likely dropped (no gain on top of H_out, #78-03).
- **Prefill kernels: two-pass (2026-11-04, from IQR's `gemm_iqr_tiled`):** decode each weight once per step into an
  int8 plane (fast), an f16 plane (accurate) or, if #46-03 passes, an int4 plane, then radiance's tuned i8a8 /
  16-bit / iu4 tile; option C below. The codes and their quantizer are unchanged by this choice, so the kernels are
  built in parallel with the quantizer experiments (`docs/research/iqr-v4.md` "Speed").
- **Engine:** radiance 1.17 (ABI 35; fork branch `qc-exl3-v3`, rebased onto each release; V3 plugin `exl3i` beside
  the frozen V1/V2 ones).
- **Evaluation data:** `eval-data.md` (xcorp 8k + a share of private agentic text for search accept / reject; calib
  verify for finals and published numbers).
- **Hardware:** 2x R9700 (TP1 for quantization and evals, TP2 at times), plus 12–16 GB consumer cards for proxies; CPU servers
  for sweeps.
- **Not in V3:** QAD (V4); decode kernels and decode-optimized variants (later); vocab-tiered embedding and
  frequency-tiered head (dropped); R1 (dropped, §7); full YAQA Sketch A / B (dead, §7); quantized vision tower /
  DFlash2 (later; V3 bundles both in bf16, §8).

## 1. Compute format (the speed)

**W/A spectrum (summary, 2026-11-05).** Weights per tensor (EXL3 trellis, K = bits / weight):

| weights | K | codebook | compute paths |
|---|---|---|---|
| sub-1 | 0.125–0.875 (1/8) | int4 grid | int4 / int8 / f16 plane (if #90 adopts it) |
| i4 | 1–3 (1/8) | int4 grid (×1.007 K2, ×1.06 K3) | **A4** (W4A4), A8, A16 |
| i8 | 2–5 (1/8), 5.25–7 (1/4) | int8-rounded mul1 (free to K6, ×1.02 K7) | A8, A16 |
| mul1 | 6–8 (1/4) | unrounded (int8 rounding ×1.35 at K8) | A16 only |
| bf16 | 16 | — | A16 only |

Activations: **A16** (f16 plane, 16-bit tile) everywhere in the accurate variant; **A8** (int8 per token × 128
inputs, other group sizes as options; +0.00005 KLD at K6) in the fast variant; **A4** (g64, i4 weights only, fast
variant ≤ 3 bpw, per-tensor knapsack option, #46-03). Shared-input groups share one mode. Fixed: LM head f16, GDN a/b
bf16/f16, and every GEMM with M < 512 (decode, small batches) on the f16 path whatever the tensor's mode: decode is
memory-bound (weight bytes), so low-bit activations save nothing there and only add error. The 512 threshold is an
assumption: the M = 16–511 sweep (below) has to confirm it, since batched decode / small prefill chunks may be partly
compute-bound. Decode-side compute that does matter is the trellis decode of the weights (4 bpw decode ~63% of
bandwidth): decode kernels are later work (BACKLOG, user 2026-11-05).

Variants: accurate + fast at every size; a third ("fastest", A4 on the MLP where cheap) at ≤ 3 bpw only if its
knapsack point is ≥ 15% lower `gemm_us` than that size's fast variant (else A4 goes into the fast variant). Sizes
2.0, 2.5–4.5 (focus), 5.0, 6.0, **7.0** (2026-11-05); 8.0 decided after 7.0 and a floor split (TODO).

- **W8A8 on int8 WMMA** (iu8 ~323 TOPS dense, E2 ~255 TOPS real at M ≥ 1024 vs our f16 path ~130–137):
  - **Weights:** EXL3 trellis codes as stored; the decoded mul1 value rounded to int8 (fixed global factor). E3:
    ×1.000–1.004 proxy error at K2–6 *when the trellis is searched with the rounded codebook*; post-hoc rounding of
    existing quants costs K5 +17%, K6 +60% (E4). So V3 requantizes everything with `--codebook i8` (§1c-bis). K7/K8
    keep the f16 tile. [2026-11-04 ladder: i8 levels run to K7 (×1.02); the mul1 K6–8 levels are f16-only.]
  - **Activations:** rotated (same Hadamard), int8 with one scale per (token, 128 inputs). E1b on K6: g128 costs
    +0.00005 KLD (~5%), per-token +0.00047.
  - **Fold (IQR-V3's, the key to FP8 speed):** the K loop sees no per-row weight scale. Per 128-input block: one
    FMA per accumulator slot with the token's activation scale (× a block factor shared by all rows); the row scale
    (EXL3's `svh`) is applied once at the store. EXL3 already has exactly this scale structure.
  - Per tensor the solver chooses the compute mode: **f16** (today's kernel) or **A8-g128**; later maybe A8 with
    other group sizes; **A4-g64** on i4 tensors at ≤ 3 bpw (2026-11-05, #46-03).
- **A4 on i4 weights: back in V3 as a per-tensor knapsack option for the fast variant at ≤ 3 bpw (user, 2026-11-05;
  #46-03).** W4A4 = int4-grid weights (the i4 ladder, K ≤ 3) × int4 activations (g64) on the iu4 WMMA; i8 / mul1
  tensors cannot take A4. The 11-01 drop and d1106's fail (#46-02: A4 on *every* MLP tensor at K2, ×1.14 unhealed /
  ×1.16 healed on the 0.8B, ≈ 0.07 bpw) were global tests; the knapsack instead puts A4 only where it is cheap.
  Steps: per-tensor A4 costs on the 27B at K2–3 (fake-quant hook per family × depth band), a real iu4 tile timing,
  then knap4 with those prices; the int4-plane kernel is built only if that knapsack picks enough A4 (rule in the
  #46-03 README). Earlier measurements, kept for reference: iu4 real GEMM ~490 vs ~255 TOPS for iu8 (E2). E1b on K6 (base
  0.00101): all linears A4-g128 +0.030; per family (per-row) gate_up +0.025 / down +0.025 / gdn_in +0.023 / attn qkv
  +0.023 / ssm_out +0.013 / attn_out +0.0075; best found: down g64 +0.0038, gate_up g64 +0.008. At 2 bpw (KLD ~0.155)
  A4-g64 on gate_up + down (~67% of the trunk FLOPs by shapes: gate_up ~45%, down ~22%; the E1b table's 28/14% was
  wrong, so the time saved is ~1.5x the old estimate) costs ~+8% KLD for an est. ~14% lower `gemm_us`; at 3 bpw the same
  is ~+45%, so A4 only pays at the bottom. Needs int4-grid codes (codebook; E3: ×1.01 at K2, ×1.07 at K3) and an
  iu4 tile with the same fold.
- **Head:** f16. At serving prefill it runs once (last token); it is not in `gemm_us`.
- **GDN a/b projections** (N = 48 and 128, bf16) stay separate `gemm_nt` ops, f16, no A8 path. **Decided
  2026-11-01 (mining merge D6):** measured share 0.27–0.4% of the step (below the ~2% bar), and a merged N = 176 op
  would misalign (10,416 / 176). Closed.
- **Decode (M = 1–16):** keep exl3r4d's GEMV; measure it against bytes/bandwidth (4 bpw: 29.4 tok/s ≈ 63% of
  bandwidth). IQR-V3's computed-code GEMV is a reference for later.
- **Open check first:** E2 measured −12…−29% for group scales at 128×128; re-measure with the fold above (activation
  scale per block, weight scale only at the store). If that is ~free, A8-g128 is the default everywhere.

## 1b. Decisions (2026-10-31)

1. **Compute mode lives in the tensor's encoding** (`act=`, group size), written per mix by `radmix` (the same quant
   can run at several modes).
2. **A8/A4 only for prefill steps of M ≥ 512**; below that the f16 path (same speed there, better quality).
3. **Group sizes are solver options**, speed vs quality: per-token, 1024, 512, 256, 128, 64 for A8 and A4
   (E0, iu8 TOPS: 64 220 / 128 265 / 256 295 / 512 312 / 1024 323; E1b, A8 on K6: g128 +0.00005, g256–1024
   +0.00015–0.00018, per-token +0.00047). Kernels instantiated per group size at compile time.
4. **Shared-input linears share one mode** (q/k/v, gate/up, GDN qkv/z). Not one activation tile, though: their input scales (`suh`)
   differ (per-tensor scale refit; signs agree), so each needs its own prep pass unless the requant ties them.
5. **Head activations: f16 only** (2026-10-31). Why, since it is easy to forget:
   - **Prefill** runs every prompt token through the trunk (each hidden state feeds later tokens' attention), but
     the head only on the **last** position: logits for earlier prompt positions would be thrown away, so the server
     does not compute them. One head row of work per request, not per prompt token.
   - **Decode** runs the head once per generated token at M = 1; speculative verify runs it at M ≈ 4–16. Both are
     below the A8/A4 threshold (M ≥ 512), so int8/int4 activations would never be used for it in serving.
   - **Exceptions:** requests for prompt logprobs (`echo` / `prompt_logprobs`) and **our KLD evals**, which need
     logits at every position: there the head runs at full M (~10% of the linear FLOPs in eval profiles). Keeping
     it f16 keeps the evals faithful to serving.
   - So the head's cost is **decode bytes**: every generated token reads all 248k × 5120 weights. Its **K** stays a
     solver option, priced like every tensor by KLD and bytes (decode time is checked at the end, not solved for);
     its activation mode does not.
6. **Embedding (a lookup, no GEMM, so no activation format):** options = V2's Lloyd/fwht128 tables (e1–e8) and a
   **trellis-coded embedding** from the requant, same quantizer as every other tensor but laid out so one row decodes
   alone (no rotation across rows); the solver picks by bytes vs KLD. Needs a row-decode gather kernel.
   Quantize it with **uniform weighting (H = I)**, like the Lloyd tables: its true Hessian is diagonal = token
   frequency, which is the dropped vocab-tiering in disguise (starves rare / multilingual tokens). Est. 2–5% KLD at
   ≤ 3 bpw (trellis-3 ≈ Lloyd-4). Plain int4/int8 tables are dominated by Lloyd at the same bits.
   **Measured (CPU, 2026-10-31, `v3/e3/embtrellis.py`):** at equal bits the trellis has 0.51–0.56× Lloyd's
   reconstruction error (K ≥ 2): ~0.48 bits a value saved = ~0.023 bpw (so trellis-3 ≈ Lloyd-3.5, not Lloyd-4);
   worth ~1% KLD at ~3 bpw by V2's fitted embedding costs. **Menu: quarter steps** (one quarter = 0.012 bpw; the
   generic pattern decode serves them at no extra kernel cost). Scale group size: one scale per row (0.003 bit/value) beats
   G128 by ~15% at equal bits; G1024/G512 lose at every K up to 5.5 (menu sweep): one scale per row only.
7. **Fresh held-out slices** ver3 (~80 docs, monitoring) and ver4 (~240, final) from the unused verify docs, plus
   search-pool selection slices; built once, frozen.
8. **Fractional K: compiled everywhere**. One instance per shift pattern for the GEMV, the narrow tile and the
   prefill pre-decode pass. The prefill GEMM itself only sees decoded int8/f16 fragments, so instances are
   patterns + (mode × group size), not their product.
9. **Speed objective = real-world prefill time** (2026-10-31). Per option, measured on card 0 at M = 2048
   (the recommended chunk), summed over the trunk; the head (last token only) and the embedding (one row a token)
   are ~0 in prefill, so the board's `gemm_us` and real prefill rank options the same (reports show both; `gemm_us`
   calibrated on the V1 entries). **Decode is not in the solve:** at a given size it is nearly fixed (and measured
   nearly flat in K below ~4 bpw -- a fixed per-token cost, not bytes: 32.5 tok/s at 1.40 vs 24 at 6.00)
   (the A8/A4 modes never run at decode M, and the K mix barely changes total bytes); decode work (GEMV per K and
   fractional pattern, the spec-decode narrow tile at M 4–16, head K) is done at the end on the chosen mixes.

## 1c. Serving and release notes (2026-10-31)

1. **Mixed batches:** the A8/A4 path triggers on the GEMM's total M, so decode rows batched with a ≥ 512-row prefill
   chunk take it too; outputs can depend slightly on batching. Accepted; documented in the model cards.
2. **Chunked prefill:** ≥ 2048-token chunks are already the recommended setting; time table measured at 2048.
3. **Separate plugin [leaning yes]:** V3 kernels in a new plugin with a new encoding name (e.g. `exl3i`), so
   V1/V2 containers keep loading through the frozen exl3r4d / exl3dense untouched (no format version bump, no risk
   to V2's byte-identity); the qwen35_exl3 architecture plugin dispatches by encoding. Shared code (trellis decode)
   copied or factored into a common header.
4. **Kernel selftest matrix:** every (mode × group) and every K pattern against a torch reference, automated. Cases
   that bit the V1 bring-up and must be in it (unit tests built on synthetic 2-D f16 operands missed all of them):
   - the real row count differs from the band's M (M = 1, 15, 511, 512, 513, 952, 2048): the op must compute
     `rows` of the operand, and the A8/A4 threshold and tile / split-K choice must see the real M;
   - bf16 and f32 output stores (the graph is bf16; logits f32), not only f16;
   - the GDN `ssm_out` input, a 3-D `[T, 48, 128]` buffer read as `[T, 6144]` (row pitch from the flat layout);
   - refusal tests for malformed K / mode / group strings in the encoding, so the gates cannot rot;
   - a per-container **census** of the resolved (kernel, K pattern, mode, group) per tensor, diffed against the
     `.mix`: a mis-parsed `act=` that silently falls back to f16 is correct and slower, invisible to KLD;
   - the loaded plugin's build hash printed (a stale `.so` was benchmarked as new more than once in V1).
   Added from the V1/V2 bring-up (mining merge A5; each of these failed silently, or only on long / TP2 runs):
   - launch structs value-initialized with a `static_assert` on their size, plus a >= 4096-token multi-replay run
     (struct padding and graph replay broke V1);
   - one stored weight form across every M band: declare-time checks at M = 1, 16, 17, 511, 512, 2048;
   - operand arity checked against the op schema;
   - the harness fails when it checked 0 cases (it reported "0 checked" as a pass before);
   - two or more scratch / split-K sizes (a chunk-size change moved KLD +1.5% while op-level checks passed);
   - `RADIANCE_OP_ORACLE` and `RADIANCE_OP_REPEAT` on a real container, not only synthetic operands;
   - device code present for gfx1201 in the bundle (a missing kernel fell back silently);
   - a finite-value assert on outputs; fits and reports refuse non-finite rows instead of skipping them;
   - refusal of any tile width other than 16K words (half-K widths 16K + 8 were accepted once);
   - the epilogue's fused `v_fma_mixlo_f16` rounding compared against the reference store;
   - K7 / K8 and every fractional pattern exercised at least once;
   - TP2 declare-shape checks (a wrong shard declaration ran finite and wrong), only if V3 ships TP2.
5. **Activation-cost model:** CPU proxy (`aqproxy.py` on activation dumps) for the shape, ~30 real probes to
   calibrate (as E1c), the stream refines with whole mixes.
6. **Submission size:** leaderboard scoring is expensive (tens of minutes a checkpoint). Score every variant
   locally and submit only the variants on our own measured frontier, in a modest number per round.
7. **Fractional K in the format (convention, 2026-10-31):** follow exllamav3 1.6.3, which already stores half-K:
   - The rate is implied by the tile width: a 256-weight tile is 16·K uint16 words (K2 32, K2.25 36, K2.5 40,
     K2.75 44), so the trellis plane is u16 `[tiles_k, tiles_n, 16K]` for every K, integer or not. K must be a
     multiple of 1/16; the menu uses quarters.
   - No pattern is stored: each rate has one canonical step mask, the even spread (KA + 0.25: 0x8888, + 0.5: 0xAAAA,
     + 0.75: 0xEEEE; step i shifts KA + bit (i mod 16) bits). exllamav3 export → radiance import → kernels all derive
     (KA, MASK) from the width; a new mask would need a new rate or a stored field (not planned).
   - Sub-1 rates (K0.25–0.75, KA = 0) add the salted 0-bit read (`viterbi_tiles_pat`): same width rule, plus a codebook
     variant flag in the encoding (`mul1s`), since a reader without the salt would decode wrong values silently.
   - Encoding string: today's EXL3 encoding plus the new fields, e.g. `exl3i:k=2.25,cb=mul1,act=a8,g=128`;
     the import derives `k` from the width and refuses a mismatch; the reader's equality check compares all fields.
   - Then grep every K gate in the plugin (V1's K=1 support touched five sites and three tests) and add refusal
     tests for malformed K / mask / act / group values to the selftest matrix.
8. **Engine version:** **[superseded 2026-11-04]** V3 targets radiance 1.17 (ABI 35, append-only; fork branch
   `qc-exl3-v3`, rebased onto each release). Original: V3 targets radiance 1.15.x (ABI 32: plugins export a layout fingerprint). Take the
   prefill-softmax fix (PR #362: rescale per row, not per wave; measured on our eval: KLD −0.12%, packed and unpacked
   runs agree with it) with the port, and re-baseline a few V2 picks on the new engine once.
9. **Output store dtype and range:** the int8 epilogue picks its store dtype fresh. Check f16 vs bf16 vs f32 rounding
   of linear outputs with the E1b hook (bf16 storage is ~1.1e-3 relative L2 a GEMM, comparable to A8-g128's cost at
   ≥ 6 bpw), and record max |y| of the residual writers (down, ssm_out, attn_output) over the long verify traces:
   the f16 tile kept for K7/K8 overflows at 65,504, and one inf costs more than any quant choice.

## 1c-bis. Codebook (2026-11-01)

- **Every V3 quant of ours is searched with the int8-rounded mul1 codebook** (`ourq.py --codebook i8`, exl3cb): free
  to K6 (GPU smoke: x1.000 K1–6, x1.02 K7, x1.35 K8). So **both decode paths must round**: the int8 path natively,
  the f16 path by decoding the rounded value (else it reads unrounded values the search never chose: E4's post-hoc
  mismatch cost K5 +17%, K6 +60%). The codebook is part of the V3 encoding (`cb=mul1i8`); V1/V2 tensors keep mul1.
- **Release scope (user, 2026-11-01; amended 2026-11-05): V3 sizes go up to 7.0** (fast + accurate; the ladder
  already holds its levels, ~3 h a variant; the speed gain is the point: V2 7.00 runs 8,105 µs vs IQR-V4's 4,006).
  **7.5 / 8.0 stay V2** (already ~0.00035 KLD or lower). So no plain-codebook (f16-only) fractional or improved high-K quants; existing plain K7/K8 (ours,
  turboderp's) remain f16 options for the top V3 sizes.
- int4 grid (`--codebook i4`): x1.007 K2, x1.02 K2.5, x1.06 K3 -- the i4 ladder (K0.125–K3); the only weights that can
  take A4 (#46-03, 2026-11-05).
- **Cubic int8 codebook i8c (2026-11-02, #78, adopted by the user):** cubic 0.02 warp of mul1 before the int8 round
  (2 FMAs in the decode; `EXL3_I8_CUBIC`, `--codebook i8c`). 0.8B KL K3 −1.7%, K2 −2.7%, K4 −2.3%; CPU proxy −1.2…−1.5%
  on the 27B tensors, every tensor (#78, #80). **Caveat (2026-11-03, #78-03): on top of diagonal H_out the 0.8B gain
  is gone at K3** (1.000 / 1.015 / 1.005; K2 mixed). The 27B check must include an H_out arm before i8c goes into
  the trunk; #78-04 adds seeds. **[2026-11-04]** likely dropped: it adds nothing on top of H_out.
- Damping: attention/GDN input groups take, per tensor, the best of sigma_reg {0.025, 0.005, 0.001} by proxy error
  against the undamped Hessian (`--sigma-in-sweep`); other families keep the default.

## 1d. turboderp's tensors (2026-10-31)

- **Options at every K**: his published EXL3 tensors join ours in V3's option set, at all bit widths (V2
  allowed only ≥ 5 bits). Cheap: containers and proxy rows exist; the knapsack drops what does not pay.
- **Why they win at high K, first:** per tensor, ours have ~23% lower proxy error at every K (0.74–0.80×; ours
  worse in only 1–4% of tensors), yet V2's picks take 104 of his tensors at 5.5 bpw, 52 at 6.0, 42 at 8.0, and the
  best ours-only 6.0 mix lost clearly on held-out data (0.00112 vs 0.00072). Either the fit's per-family factor
  (KLD per unit of input-side proxy error) differs for real, or it is a fitting artifact plus selection noise.
  **Early V3 experiment:** single-group swaps ours-K5 vs his K5 (and K6) on the same tensors at ~4 depths,
  measured end to end. If his win despite worse proxy error, the input-side proxy misleads at high K: then
  output-side Hessians (YAQA) or calibrating on model-written text (as his self-calibrated "SC" quants do) should
  shape the V3 requant.
- **Free evidence first (CPU):** his repository ships per-tensor tables for this model (`kld_table.json`: a
  sensitivity S and KLD at K1–8 from trace-based noise attribution; `measurement.json`: per-group 2→3-bit dKLD), and
  his recipes give ~22 tensors the top K and ~65 the next one at each size. Rank-correlate S with kfit2's
  sensitivities, and intersect his top-K tensors with the ones V2 takes from him: a large overlap means his trace
  sees something our input-side proxy does not. (Done 2026-10-31: his S vs our fit Spearman 0.71, weak within families: not
  used as a per-tensor prior; sub-2 options are priced from our own measurements.) And read where his SC calibration trace (self-sampled, ~250 × 2048 tokens) enters: the GPTQ
  Hessian, or only the allocation. **[2026-11-04 answer]** Both: per exllamav3's `doc/optimize.md`, the self-sampled
  trace (~140 seeded conversations, 19 languages, default sampling; 217 rows, 509k generated tokens, from the
  model repo's main branch) feeds the LDLQ Hessians (`-cd`), the measurement and the
  recipe. V2's fit priced his plain tensors at 1.23× his SC tensors' real KLD per unit proxy error: suggestive

## 4. Solver

- **[current, 2026-11-04]** knap4: min KLD s.t. bytes ≤ B with per-tensor compute modes (f16 / A8 / A4) and a speed
  budget per variant; it also needs a decode table (bytes and ALU per token) to report decode. Shared-input groups

- **Held-out sources (2026-11-01, `eval/pools/provenance.py`, `amend.py`):** of 845 verify docs only 317 (434k

  affects all arms of a comparison equally); the moved docs were in the qad head Fisher (slab-head ranking).

  calls agree at 0.993-0.997; spend the saved time on more documents). **Held-out monitor: 8k.** It scores the

  are cut from the published bf16 reference (`challenge/golden/calib`); no reference run is needed.
- **Budget and stop rule (user, 2026-11-01):** no fixed budget (expect ~1,500–3,000 evals with the larger menu;
  ~30 evals/h a card, int8 evals ~25% faster). **Each size band stops when its held-out score stops decreasing:** the
  ver3 score of the band's best-so-far mix has not improved by more than its paired SE over the last N ver3 reads
  (N fixed before the run). **ver3 is read for ~1 eval in 10:** only candidates that become their band's best on the
  search slice (V2's ratio), which saves eval time and keeps ver3's selection bias low. V2's long tail was deliberate (spare overnight compute), not a mistake. Fewer targets (release
  sizes only), short high-bpw phases (V2's 6 h one bought ~nothing).
- **Eval runner: a resident base (proposal, 2026-11-02; not started).** V2's eval cost ~80 s fixed + ~0.4 s per 1k
  positions: on 200-300k-position slices the fixed part is about half. Why it is not a small patch: a candidate differs
  from the last one in a handful of weights, but a swap can change a weight's stored size (another K) and its op's
  kernel row (exl3 <-> exl3i), so the program is rebuilt; only the unchanged weights' device memory and the declare's
  plan can be kept. Steps, each gated: (1) **measure first** -- split the 80 s on the R9700 (container read from page
  cache, relayout, upload, graph build, warmup, scoring) with one eval under timers; if load + relayout + upload is
  < 30 s the feature is not worth an engine change (cheaper: keep the container in page cache, a ramdisk for the mix,
  two evals a card). (2) If it is: a `--kld-serve` mode in the fork -- the engine stays up, reads "swap <mixfile>"
  lines, re-declares, keeps every weight whose (name, encoding, bytes) is unchanged in place (same device address,
  no relayout), loads the rest, re-scores. (3) Gate: per-row scores byte-identical to a cold load of the same mix
  on 20 candidates (V2 and V3 encodings, K up and down, exl3 <-> exl3i), and no device-memory growth over 200 swaps.
- Long-context check: one card fits the 262k bf16 KV up to ~5 bpw on 1.13 at step 2048 (5.00: 255k, 6.00: 209k

## 6b. Finer K: what to build (2026-10-31)

- **[superseded 2026-11-04 by the ladder in Goal and scope; sub-1 is in V3]** Build the trellis generically once (per-position shift pattern → any rational K). **Menu: quarter steps K1–K5,
  half steps K5–K6.5** (V3 stops below 7 bpw; K7 / K8 from existing quants). Quantize in order of use: 2.25–4.75,
  then 1.0–2.0, then 5.5–6.5. **Sub-1 K (K0.125–0.875): V3.5, not in the V3 menu (decided 2026-11-01); no K0.**
  They only matter for the < 2 bpw sizes, which are not a focus, and need the salted 0-bit read in the quantizer and
  every decode kernel. Caveat (mining merge B16): knap4's "nothing below K1.5 picked at 2.5" came from a menu with
  no sub-1 options; the cheap check before reviving them is proxy-priced K0.5 / K0.75 options in knap4 at 2.0–2.5. Heads at half steps (one K step of the head is 0.047 bpw; a half step
  halves the rounding the trunk has to absorb); quarter-step heads are the fallback if the row-slab head (§2) fails
  (a quarter step = 0.012 bpw, near the trunk's own granularity; cost: head quant runs only).
- **The quantizer side already exists for K ≥ 1 (found 2026-10-31):** exllamav3 1.6.3 (the build on the GPU box)
  quantizes half-integer K: `frac_k`, `quantize_tiles_frac_kernel<KA, MASK>`, step width = KA + bit (i mod 16) of a
  16-bit mask (rate KA + popcount/16, in 1/16-bit steps), tile = 16K uint16 words. Only MASK 0xAAAA (KA + 0.5) is
  instantiated, for KA 1–3 in the reference checkout; quarter steps are new instances (0x8888 = KA + 0.25, 0xEEEE =
  KA + 0.75, same even spread as the CPU test) and KA up to 7. **Sub-1 (KA = 0) is not covered:** a 0-bit step
  would repeat the previous state's value; it needs the salted read of the CPU test (`viterbi_tiles_pat`), new in
  the quantizer and every decode kernel. The serving side (our radiance plugin) needs the pattern in GEMV, the
  narrow tile and the prefill pre-decode regardless.
- **Below K2 the damage steepens (measured 2026-10-31):** our proxy error falls 2.11 bits per bit from K1 to K2
  (2.00 from K2 to K3, 1.97–1.88 above), and V2's fitted model (KLD ∝ proxy^1.004, one factor for K1–K3)
  under-predicts the K1-dominated swaps by 20% in-sample, 36% cross-validated (K2: 5%, K3–K8: ±1–4%; only three
  K1 swaps). The real K1→K2 slope is ~2.3–2.5 bits per bit, matching turboderp's note (~2.35 vs ~2.0 on this
  model). So: price every sub-2 option from measurements, never by extrapolating the proxy; give K1 and each sub-2
  level its own family factor in the fit; sub-1 at 1/8 steps from K0.125 (user, 2026-11-01).
- Sub-2 steps matter only for the 1.5–2.0 bpw sizes. Below 1 bit the trellis keeps little (Gaussian
  D(R) = 2^-2R: K0.25 removes ~29% of a weight's error energy, K0.5 50%, K1 75%), so they suit only very insensitive
  tensors. K0 (drop the tensor) dropped (user, 2026-11-01): K0.125 costs only 0.125 bit a weight more and still
  removes ~16% of the error energy (Gaussian D(R)), a fifth of what K1 removes. Continuous K beyond
  quarter steps: < 1% more, each K costs a quant run → no.
- Row-slab K (a K per 128-row slab inside a tensor): deferred for the trunk. E3c put its ceiling at ~0.05 bit, but
  E3c saw only the input-side Hessian, which cannot tell rows apart; the output-side Hessian (YAQA's H_out diagonal)
  could, but output-side weighting hurt in every form we tried (gates 2–2e): row-slab K for the trunk is dropped. Needs a K per slab and per-slab scales in the format.
  **[2026-11-04]** The diagonal H_out now helps (#33-16), so the reason above no longer holds: a row-slab ceiling test
  with Σdy² row importance is proposed (CPU proxy, not yet approved).
  **For the LM head it is being tested now** (the head's Fisher diagonal is cheap: Σ p(1−p) from the bf16 golden's
  top-512 -- truncated, not exact; no backward). Result: −36…−40% head KL at K5–6 budgets (headsim). The head is
  ~5–7% of total KLD by the log's own numbers (not 1.5–3%), so ≈ −2…−3% total at 3–5 bpw; add the rare-token guard
  KL to the slab price (x1.2–1.5 at K5–6) and keep the K3 floor, see §2.

### A1. int4 compute (iu4 WMMA), measured 2026-10-30, card 0

gfx1201 has **no fp4/fp6** (`wmma_f32_16x16x128_f8f6f4` needs gfx1250-insts), but it has an **iu4 WMMA at twice the
8-bit rate**. Peak, 8 independent accumulators per wave (`v3/bench/wmmabench.hip`; ISA checked, 8 WMMAs/loop):

| op | TOPS |
|---|---|
| iu8 16x16x16 / fp8 16x16x16 | 323 / 321 |
| iu4 16x16x16 | 328 (old shape, no gain) |
| **iu4 16x16x32** | **685** |

- iu4 is int4 x int4 (a sign flag per operand). The 2x needs **W4A4**: 4-bit weights *and* 4-bit activations.
- **Scales:** i32 partial sums must be scaled whenever a scale changes along K (`v3/bench/wmmagrp.hip`, 16x16
  tiles; the naive bench without scaling already runs at 460):

  | group along K | float (cvt + fma) | i32 multiply |
  |---|---|---|
  | 32 | 248 | 136 |
  | 64 | 366 | 236 |
  | 128 | 484 | 363 |

  -> i32 multiply is slow (quarter rate). Use a **per-output-channel weight scale and a per-token activation scale**
  (epilogue only, free), or groups of >=256 along K. Rotation (Hadamard) is what makes per-channel W4 tolerable
  (QuaRot/SpinQuant recipe). Weight codes must be uniform int4 (no codebook) to feed iu4 directly.
- **Benchmark pitfall:** identical accumulator chains or loop-invariant inputs get CSE'd (first runs showed
  1800 "TOPS"). Always count `v_wmma` in the ISA (`--save-temps`).
- **What iu4 buys:** prefill only. Decode is bandwidth-bound (4.0 bpw: 13.7 GB x 29.4 tok/s = 403 GB/s of ~640), so
  there only bytes and dequant cost matter; uniform int4 with a trivial unpack should get close to bandwidth
  (~1.3–1.4x decode headroom). Prefill now ~100 TF effective (1848 tok/s at 8k), mostly linears.
  - Ceilings: 8-bit ~3x, iu4 ~6.5x on the linears.
  - Realistic share of peak for a real kernel is ~50–65%; attention, GDN and norms don't speed up.
  - Guess: 8-bit ~1.7–2x end-to-end prefill, W4A4 ~2.5–3x.
- **Quality risk:** published W4A4 (QuaRot, SpinQuant) loses noticeably on 8B-class models. Expect KLD >= 0.05 for
  W4A4 everywhere, which is well above the 0.01 goal. So W4A4 has to be a **per-tensor option** chosen by
  sensitivity, not the whole model.
- **Precision menu per linear** (each is its own GEMM, so mixing per tensor has no kernel problem):

  | option | how | speed |
  |---|---|---|
  | W4A4 | one iu4 pass | 1x |
  | W4A8 | activation split into hi/lo nibbles, 2 iu4 passes on raw int4 weights (no weight dequant at all) | ~0.5x |
  | W8A4 | weight split into nibbles | ~0.5x |
  | W8A8 | iu8/fp8 | ~0.5x |
  | f16 | | ~0.25x |

  - **Within a tensor (Atom-style):** reorder K so outlier activation channels form the first K blocks. Those blocks
    get the 2-pass (A8) treatment and the rest a single pass, with cost (K + K_out)/K.
  - **Constraint:** linears reading the same activation (qg/k/v, gate_up) should share the A precision, or that input
    is quantized twice (cheap, but two outputs of the norm kernel).
- **Decision (2026-10-30):**
  - **Base format = W8A8 compute:** any weight code (1–8 bit) decoded to int8/fp8. W4A8 is dropped. It runs at the
    same speed as W8A8 (two iu4 passes) and would force uniform int4 storage.
  - **W4A4 = a per-tensor option**, only where its activation cost is small. It is plausible for <=0.05 KLD at
    3–3.5 bpw, tight for 0.01 at 4 bpw, since the weights already use ~0.008 there.
  - Amdahl: half the linear FLOPs at int4 -> GEMM time ~0.75x of all-8-bit.
  - Likely candidates: gate_up, attention/GDN input projections. ffn_down (post-SwiGLU outliers) likely not.
  - A full-model W4A4 quant is an optional side experiment, for speed curiosity only.
- **Knapsack fit:** add **time** as a second cost (per option, from a kernel microbench). Then solve
  min KLD s.t. bytes <= B and prefill time <= T, or a Lagrangian. The surrogate and DP machinery carries over;
  activation-quant cost per tensor comes from experiment E1b.

### A2. Decode-design candidates (2026-10-30)

Candidates (all keep a trellis/vector code for the bits, differ in the decoded value):
- **A. Trellis on an int8 grid** (IQR-V2/V3 route): each state maps through a trained table to an int8 value; per
  (row-block x 128) scale folded once per k-block in the i32 accumulator. Decode = shift + mask + table lookup
  (IQR: one table lookup per weight; V2 found the *lookups* bound the speed, V1's scalar tables are faster).
- **B. EXL3-style computed codebook (hash) to fp8** instead of f16: keeps EXL3's quantizer almost unchanged, but the
  hash is ~50 VALU a 16x16 tile — the very thing that competes with WMMA issue. Only viable as a two-pass decode
  (decode once per step into fp8 fragments, like our T2 — half the bytes of f16).
- **C. Two-pass everywhere** (our T2 generalised): any code -> 8-bit fragments in a pre-pass, then a pure 8-bit GEMM.
  Pre-pass cost is fixed per weight per step (~10% now at f16; half at 8-bit) and is amortised by packing documents.
  Simplest kernel; decouples code design from GEMM design. Probably the first prototype.
Decision driver: decode VALU per weight (fused, A) vs pre-pass bytes (C). A fully optimised fused
trellis dequant with a table goes LDS-bound (IQR-V3 report §2: table gathers bound the GEMV); recomputing values
beats staging them.
